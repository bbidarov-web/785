# Контур 785 — подготовка к переносу на сервер

Документ для разработчика, который переносит демо на сервер. Демо полностью работает в браузере: данные лежат в `localStorage`, между вкладками они синхронизируются через `platform.js`. Перенос — это замена хранилища и проверок на API. Интерфейс при этом не переписывается.

## 1. Состав проекта

| Файл | Что это | Кто работает |
|---|---|---|
| `Админ-панель.dc.html` | Панель платформы, рабочее место собирается по роли | администратор платформы |
| `Кабинет методиста.dc.html` | Та же панель с `locked-role="methodist"` | методист |
| `Кабинет менеджера по продажам.dc.html` | То же, `sales_manager` | менеджер |
| `Кабинет руководителя продаж.dc.html` | То же, `sales_head` | руководитель продаж |
| `Личный кабинет ВКК.dc.html` | Кабинет клиники | админ клиники, ответственный за ВКК |
| `Кабинет исполнителя.dc.html` | Вход по ИНН клиники и телефону, только свои назначения | медсестра, исполнитель |
| `Обход - мобильный.dc.html` | Мобильный обход: чек-листы, журналы, фото | аудитор, исполнитель |

Места, где нужен сервер, отмечены в коде комментариями `// SERVER:` — это прежде всего `auth.js`. Там же указан предполагаемый метод и путь API.

## 2. Арендатор и изоляция

- Арендатор — клиника, ключ — **ИНН**: 10 цифр для юрлица, 12 для ИП, с контрольной суммой ФНС. ИНН сквозной для всех экранов.
- В демо данные клиники лежат под ключами вида `k785_<канал>_<ИНН>`.
- На сервере ИНН арендатора берётся **только из сессии**, а не из параметра запроса. Кабинет исполнителя в демо уже так работает: ИНН берётся из учётной записи.
- Сотрудник платформы видит всех арендаторов в границах своих прав. Сотрудник клиники видит только свою клинику.

## 3. Каналы данных → таблицы и API

Полная карта полей — в «Сопоставлении кабинетов». Основные каналы:

| Ключ в демо | Сущность на сервере | Пишет | Читает |
|---|---|---|---|
| `k785_accounts`, `k785_session` | users, sessions | auth | все |
| `k785_clinics` | tenants (ИНН → название) | клиника, оператор | все |
| `k785_admin_state` | справочники платформы: эталоны, тарифы, каталоги, типы документов, штат | платформа | платформа, клиники (часть) |
| `k785_client_state_ИНН` | рабочее состояние клиники | клиника | клиника, оператор |
| `k785_stagedocs_op_ИНН`, `k785_blockdocs_ИНН` | состав документов по этапам и блокам | оператор, клиника | обе стороны |
| `k785_doc_grants_ИНН` | **выдача документов клинике** (кто, когда, этап) | платформа | клиника, оператор |
| `k785_stage_paid_ИНН` | подтверждённая оплата этапа | платформа | клиника |
| `k785_docasg_ИНН` | матрица ответственных «документ → исполнитель» | клиника, оператор | клиника, исполнитель, обход |
| `k785_doc_notes_ИНН` | комментарии клиники к документам | клиника | оператор |
| `k785_messages_ИНН`, `k785_msg_ack_ИНН`, `k785_broadcasts` | рассылки методиста и квитанции о прочтении | платформа, клиника | обе стороны |
| `k785_audit_plan_ИНН`, `k785_walk_results_ИНН` | план проверок и результаты обходов | клиника, обход | клиника, оператор, исполнитель |
| `k785_equip_pos_ИНН`, `k785_equip_fill_ИНН` | оборудование и заполнение журналов | клиника, обход | все три |
| `k785_selfaudit_ИНН` | прогоны самообследования | клиника | оператор |
| `k785_op_queue` | очередь работы оператора (взял / отложил / закрыл) | платформа | платформа |
| журнал действий (`LOGKEY` в панели) | audit_log, **только добавление** | платформа | платформа |

Правило переноса: одна запись канала — одна строка таблицы с `tenant_inn`, `updated_at`, `updated_by` и `version`. Сейчас каналы пишутся целиком. На сервере запись должна идти построчно с проверкой версии, чтобы одновременные правки двух сторон не затирали друг друга. Место конфликта уже обработано в демо для состава подэтапа — там пример слияния.

## 4. Роли и права

Матрица — `ROLES` в `platform.js`. Это единый источник правды: сервер должен проверять **ту же** матрицу на каждом эндпоинте.

- Платформа: `platform_admin`, `methodist`, `sales_manager`, `sales_head`.
- Клиника: `clinic_admin`, `vkk_lead`, `nurse` (исполнитель), `auditor`, `observer`.
- Права выданы на действия, а не на экраны. Примеры: `standard:publish`, `money:write`, `doc:grant`, `role:manage`, `bulk:money`, `second:money`.
- **Вторая рука** — семь необратимых операций подтверждает второй сотрудник, своей же рукой провести нельзя: повышение роли, публикация эталона, публикация тарифов, удаление тарифа, массовая операция больше 20 клиник, подтверждение оплаты от 100 000 ₽, выдача документов без оплаты. На сервере это двухшаговая сущность «запрос → подтверждение» с разными `user_id`.
- **Ответственный менеджер** (`clinicManager` в состоянии панели): менеджер по продажам выдаёт документы только по закреплённым за ним клиникам. Руководитель продаж, методист и администратор — по всем.
- **Заявка сотрудника платформы** на доступ создаёт запись с `pending: true`, войти по ней нельзя. Роль назначает администратор (`approveAccount`), запрошенная роль — только пожелание.

## 5. Выдача документов клинике

1. Клиника оплачивает этап. Оплата онлайн активирует этап автоматически, по счёту — после подтверждения оператором (`k785_stage_paid_`).
2. Оплата открывает **состав** этапа, но не шаблоны.
3. Методист, менеджер или администратор выдаёт документ: поштучно или «Предоставить все» по подэтапу или блоку. Запись: `{ by, role, at, stage, code }`.
4. Клиника видит невыданный документ в перечне с плашкой «ожидает выдачи», но открыть его не может.
5. Каждая выдача и каждый отзыв — запись в журнале действий.

На сервере: выдача — отдельная таблица `document_grants`. Эндпоинт шаблона отдаёт содержимое только при наличии выдачи — это проверка на API, а не в интерфейсе.

## 6. Что сделать на сервере — по приоритету

1. **Аутентификация.** httpOnly-cookie вместо `k785_session`, хеш пароля bcrypt или argon2 вместо отпечатка, 2FA и сброс пароля через реальный шлюз смс и почты. Сейчас код показывается на экране — это только для демо.
2. **Проверка прав на каждом эндпоинте** по матрице `ROLES`, арендатор берётся из сессии.
3. **Журнал действий** — таблица только на добавление, без UPDATE и DELETE, с подписью записи (хеш-цепочка или подпись сервера).
4. **Хранилище файлов**: объектное хранилище, версии, проверка на вирусы, выдача по подписанной ссылке. Демо хранит содержимое в браузере.
5. **Офлайн-очередь обхода**: у каждой операции идентификатор, повтор до подтверждения сервера, защита от дублей по идентификатору, слияние по версии записи.
6. **Почта**: дайджест оператору, уведомление о подтверждении доступа, напоминания клиникам о сроках и продлениях.
7. **Платёжный шлюз**: эквайринг, счёт-оферта, автопродление с уведомлением. Точки подключения отмечены в кабинете клиники (раздел оплаты).
8. **Фоновые задачи**: массовые операции с прогрессом и защитой от повтора, пересчёт сроков, напоминания.

## 7. Что уже убрано в пакете для переноса

В `prototype/` это уже сделано:
- демо-учётные записи выключены — `seedDemo()` срабатывает только при `window.K785_DEMO = true`;
- автовыдача демо-документов отключена;
- поля входа пустые, без подсказок с логинами и паролями, пустой вход отклоняется;
- переключатель «Роль · демо» скрыт, роль берётся из сессии;
- коды 2FA и сброса пароля не возвращаются в ответе и не показываются.

Осталось при переносе: заменить начальные значения `state` (демо-клиники, подписки, штат) данными из API. Эталонные справочники — блоки, типы документов и оборудования, чек-листы, цикл, тарифы — перенести как начальные данные миграции.

**Первый администратор платформы** создаётся командой на сервере при развёртывании, с обязательной сменой пароля при первом входе. Дальше он подтверждает заявки остальных.

**До запуска решить:** хостинг в РФ и уведомление Роскомнадзора (152-ФЗ); провайдеры смс, почты и эквайринга; утвердить пороги второй руки (в прототипе 20 клиник и 100 000 ₽, константы `SECOND_BULK` и `SECOND_SUM`).

## 8. Миграция данных пилотных клиник

Если пилот шёл на демо, данные выгружаются из `localStorage` по списку ключей из раздела 3, раскладываются по `tenant_inn` и загружаются в таблицы. Старые ключи вида «префикс + название клиники» кабинет сам переносит на ИНН при первом открытии — перед выгрузкой откройте кабинет каждой клиники один раз.

## 9. Проверка после переноса

- Вход под каждой из девяти ролей: видна только своя зона, чужая роль в кабинет роли не пускается.
- Исполнитель видит только назначенные документы, проверки и журналы.
- Невыданный документ не отдаётся API даже по прямому запросу.
- Операция второй руки не проводится одним пользователем.
- Запись журнала нельзя изменить или удалить.
- Две вкладки правят один подэтап — изменения сливаются, а не затираются.
- Обход без сети: результат доходит один раз, без потерь и дублей.
