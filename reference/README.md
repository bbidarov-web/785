# Контур 785 — пакет для Claude Code

SaaS для внутреннего контроля качества и безопасности медицинской деятельности (Приказ Минздрава № 785н). Платформа ведёт клиники от первичной диагностики до работающей системы качества: документы по этапам, обходы с чек-листами, нарушения и корректирующие мероприятия, журналы по оборудованию, самообследование перед проверкой надзора.

## Что лежит в пакете

```
handoff_k785/
├── README.md        — этот файл: продукт, экраны, дизайн-токены, порядок работы
├── SERVER.md        — архитектура переноса: арендаторы, каналы → таблицы, права, API
├── CLAUDE.md        — правила для Claude Code в новом репозитории
├── prototype/       — рабочий прототип (HTML + JS), эталон поведения и вида
├── screenshots/     — ключевые экраны
└── docs/            — продуктовые документы и карта обмена данными
```

## О прототипе

Файлы в `prototype/` — **рабочий прототип в HTML**, а не код для прямого переноса в прод. Он показывает точный вид, поведение, права и сценарии. Задача — **воссоздать его в выбранном стеке** на сервере с базой данных. Рекомендуемый стек, если своего нет: TypeScript, React (Next.js) на фронте, Node или Python на бэке, PostgreSQL, объектное хранилище для файлов.

Экраны написаны как «Design Components» (`*.dc.html`): разметка с дырками `{{ }}` плюс JS-класс логики (`renderVals()` отдаёт значения в разметку). Среда выполнения — `support.js`; её переносить не нужно. Каждый файл открывается в браузере напрямую, если раздать папку локальным веб-сервером (`npx serve prototype`).

Все данные прототипа лежат в `localStorage`. Модуль `platform.js` синхронизирует их между вкладками — так видно, как кабинеты связаны между собой. Порядок замены этого слоя на API описан в `SERVER.md`.

**Точность:** high-fidelity. Цвета, шрифты, отступы, тексты и состояния финальные — их нужно воспроизвести точно.

### Подготовка к переносу уже сделана

- Демо-учётные записи не создаются. `seedDemo()` срабатывает только при `window.K785_DEMO = true` — для локальной разработки.
- Поля входа пустые, без подсказок с логинами и паролями.
- Переключатель «Роль · демо» убран, роль приходит только из сессии.
- Код 2FA и код сброса пароля больше не возвращаются в ответе и не показываются на экране. Места отправки по смс и почте отмечены `// SERVER:`.
- Автовыдача демо-документов отключена.

### Что осталось фикстурой

Начальные значения `state` в экранах — демо-клиники, подписки, штат, тарифы, эталонные каталоги. Они показывают, какие данные нужны экрану и в какой форме. На сервере эти данные берутся из API.

Эталонные справочники стоит перенести как **начальные данные миграции**, а не удалять: каталог блоков контроля, типы документов, типы оборудования, проверочные листы, годовой цикл, тарифы. Это содержательная работа методистов.

## Кабинеты и роли

| Файл | Кабинет | Роли | Вход |
|---|---|---|---|
| `Админ-панель.dc.html` | Панель платформы | администратор платформы | ИНН компании + логин + пароль |
| `Кабинет методиста.dc.html` | та же панель, `locked-role="methodist"` | методист | то же, чужая роль не пускается |
| `Кабинет менеджера по продажам.dc.html` | `locked-role="sales_manager"` | менеджер | то же |
| `Кабинет руководителя продаж.dc.html` | `locked-role="sales_head"` | руководитель продаж | то же |
| `Личный кабинет ВКК.dc.html` | Кабинет клиники | админ клиники, ответственный за ВКК, аудитор, наблюдатель | ИНН клиники + логин + пароль |
| `Кабинет исполнителя.dc.html` | Кабинет медсестры или исполнителя | исполнитель (`nurse`) | ИНН клиники + телефон + пароль |
| `Обход - мобильный.dc.html` | Мобильный обход | аудитор, исполнитель | через кабинет клиники |

Матрица прав — `ROLES` в `prototype/platform.js`. Это единый источник правды, сервер проверяет ту же матрицу. Права выданы на **действия** (`money:write`, `standard:publish`, `doc:grant`, `role:manage`…), а не на экраны. Чужой раздел открыт только для чтения, с плашкой.

## Экраны и ключевые сценарии

### Панель платформы
- **Дашборд** по группам: финансы (MRR, ARPA, выручка на клинику), подписки (востребованность тарифов, срок жизни, отток), активность и внедрение (срок внедрения по этапам, дисциплина журналов, доля заполнений на месте).
- **Каталог клиентов**: поиск по ИНН, множественный выбор и групповые операции в три контура — предпроверка каждой клиники, предпросмотр с построчным «что произойдёт», отчёт и откат.
- **Карточка клиники**: этапы и блоки вкладками, выдача документов, ответственный менеджер, комментарии клиники, корректирующие мероприятия цепочками по кругам проверок.
- **Подписки и заказы**: сводный список в хронологии со статусами, корзины без оплаты, оплата этапов. Вкладки переставляются.
- **Очередь работы**: задача → «взял / отложил / закрыл», дайджест за сутки.
- **Сообщения от методиста**: рассылка текста, файлов и комментария с квитанциями о прочтении.
- **Эталоны**: блоки контроля, типы документов, чек-листы, годовой цикл — редакции, восстановление и пилотный тираж.
- **Журнал действий**, **Роли и права**, **Профиль компании**: штат и заявки на доступ.
- **Вторая рука** — семь необратимых операций подтверждает второй сотрудник: повышение роли, публикация эталона, публикация тарифов, удаление тарифа, пачка больше 20 клиник, оплата от 100 000 ₽, выдача без оплаты.

### Кабинет клиники
Этапы внедрения 1–4 с подэтапами и блоками. Документы открываются уже заполненными: бланк выбирается по виду документа, в переменные подставляются реквизиты профиля и ответственный по направлению. Опись документов. Обход и аудиты. Корректирующие мероприятия. Оборудование и журналы. Самообследование с выгрузкой пакета для инспектора. Сотрудники и матрица ответственных. Сообщения от методиста.

### Кабинет исполнителя
Только то, где сотрудник назначен: документы из матрицы ответственных, проверки из плана, журналы по оборудованию. Отметка «Выполнено». Переход в обход.

### Мобильный обход
Чек-листы с ответами, комментариями и фото. Нарушение само становится мероприятием. Формы журналов по оборудованию. Работа без сети.

## Выдача документов (важная бизнес-логика)

Оплата этапа открывает **состав** документов, но не шаблоны. Каждый документ выдаёт клинике сотрудник платформы: методист, менеджер по своей клинике или администратор. Выдача бывает поштучно или «Предоставить все» по подэтапу. Запись выдачи: `{ by, role, at, stage, code }`. Клиника видит невыданный документ с плашкой «ожидает выдачи». Каждая выдача и отзыв пишутся в журнал. На сервере шаблон отдаётся API **только** при наличии выдачи.

## Адаптивность

- **До 1100 px:** боковое меню уезжает в выдвижную панель с кнопкой-бургером.
- **До 720 px:** многоколоночные строки таблиц складываются в карточку, заголовки колонок скрываются.
- **Сенсорные экраны:** кнопки не ниже 44 px, поля не мельче 16 px (иначе iOS увеличивает страницу при фокусе).
- **Обход:** рабочая колонка до 680 px.

Правила лежат в `<helmet><style>` каждого экрана.

## Порядок работы

1. Прочитать `SERVER.md` и `docs/Сопоставление кабинет и обход.dc.html` — это карта всех каналов данных: кто пишет, кто читает, какие поля.
2. Спроектировать схему БД по разделу 3 `SERVER.md`. Каждая таблица с `tenant_inn`, `version`, `updated_at`, `updated_by`.
3. Аутентификация и сессии, затем проверка прав на каждом эндпоинте по `ROLES`.
4. Перенести экраны по одному, сверяя с прототипом: кабинет исполнителя → обход → кабинет клиники → панель.
5. Журнал действий только на добавление, хранилище файлов, офлайн-очередь обхода, почта и смс, платёжный шлюз.
6. Пройти чек-лист проверки из раздела 9 `SERVER.md`.
