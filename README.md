# Контур 785

SaaS для внутреннего контроля качества и безопасности медицинской деятельности
(Приказ Минздрава №785н). Продакшн-реализация прототипа из `reference/`
(`reference/README.md` — продукт и дизайн-токены, `reference/SERVER.md` —
архитектура переноса, `reference/CLAUDE.md` — неизменные правила продукта).

## Статус переноса

Перенос идёт по порядку из `reference/SERVER.md` §6: исполнитель → обход →
клиника → панель. Все четыре кабинета из этого порядка в рабочем состоянии, с
полным основным циклом каждого. Инфраструктура и общая логика (auth, RBAC,
журнал действий, вторая рука, выдача документов) — фундамент для всех
кабинетов — готовы полностью.

| Слой | Статус |
|---|---|
| Схема БД (`apps/api/prisma/schema.prisma`) | готово |
| Аутентификация: пароль (argon2), 2FA, сброс пароля, сессии в БД | готово |
| RBAC — матрица `ROLES` проверяется на каждом эндпоинте | готово |
| Журнал действий (append-only, включая отказы) | готово |
| «Вторая рука» — единый движок для ЛЮБОЙ операции по типу запроса | **готово все семь**: повышение роли, публикация эталона, публикация/удаление тарифа, массовая операция >20 клиник, подтверждение оплаты от 100 000 ₽, выдача документа без оплаты |
| Выдача документов клинике (grant/revoke, версии) | готово |
| Версионированные каналы данных + идемпотентность по `opId` | готово |
| Объектное хранилище файлов (фото/документы) | готово, адаптер — локальный диск (см. «Что дальше») |
| **Кабинет исполнителя** | **готово end-to-end** (API + UI, `/executor`) |
| **Мобильный обход** | **готово**: «Аудиты» (с офлайн-очередью), «Оборудование» и «Сводный отчёт» — те же эндпоинты и права, что у `/clinic` (API + UI, `/walk`) |
| **Личный кабинет ВКК** | **готово**: этапы и документы с оплатой (плюс оффер этапа — клиника явно принимает условия до заказа) со скачиванием в DOCX/PDF, профиль клиники (реквизиты — источник переменных шаблонов), опись документов с печатью в PDF, сотрудники и матрица, заявки на доступ к клинике (закрывает саморегистрацию незнакомца по публичному ИНН) с закреплением за филиалом, план проверок, годовой цикл (разбор и генерация плана, сроки CAPA по степени критичности из каталога методиста), филиалы (с изоляцией доступа — сотрудник видит только свой), оборудование и журналы, сводный отчёт, самообследование с CAPA (включая формальную проверку эффективности мероприятия), находки → корректирующие мероприятия (API + UI, `/clinic`) |
| **Панель платформы** | **готово**: публикация эталонов методистом (через вторую руку), подтверждение и приёмка оплаты этапа, тарифы и подписки клиник (со сводкой «активные/истекают/просрочены/выручка/к оплате»), массовые операции по каталогу клиентов с откатом и фоновым применением больше `SECOND_BULK` клиник (прогресс — `/api/panel/bulk/jobs/:id`), очередь работы (просрочки как задачи с общим состоянием + автоматический дайджест по расписанию), финансовый дашборд и портфель (MRR/ARPA/отток/готовность/обходы за период), каталог клиентов с фильтрами и добавлением клиники, CSV-экспорт, заявки на доступ, вторая рука на все семь операций, проверка целостности журнала действий (`/api/admin/audit-log/verify`) — четыре самостоятельных кабинета по ролям (API + UI, `/panel`, `/panel/methodist`, `/panel/manager`, `/panel/head`) |
| Docker / деплой на VPS / rollback | готово |
| CI (typecheck + тесты + сборка) | готово (`.github/workflows/ci.yml`) |

**Не готово к продаже прямо сейчас** — честно, по `reference/SERVER.md` §7:
провайдер SMS/email подключён (`infra/providers/httpNotifier.ts` — SMS.ru/Resend,
активируется ключами в `.env`; без ключей — `ConsoleNotifier` для дев-стенда),
но конкретные провайдеры не проверены на реальной отправке; платёжный шлюз
(оплата этапа сейчас — счёт с ручным подтверждением оператором, без эквайринга),
хостинг в РФ + уведомление РКН (152-ФЗ). Список полностью — раздел «Что дальше» ниже.

Сервисы (`AuthService`, `SecondHandService`, `DocumentService`, `ExecutorService`,
`WalkService`, `StaffService`, `PlanService`, `CapaService`, `StageService`,
`CycleService`, `BranchService`, `EquipmentService`, `SummaryService`,
`SelfAuditService`, `CatalogService`, `PaymentService`, `DashboardService`,
`TariffService`, `SubscriptionService`, `BulkOperationService`, `WorkQueueService`,
`ProfileService`, `InventoryService`)
работают через порты (`domain/ports.ts`) и не знают, что за ними — Postgres или
память. Это не архитектурная мода: именно поэтому у нас **285 честных тестов**
(shared 21 + api 264), которые гоняются без поднятой базы данных за секунды, и
HTTP-интеграционные тесты (`src/http/app.test.ts`), проверяющие реальные
cookie-сессии, 401/403 и полные цепочки продукта — «клиника заводит проверку →
обход находит нарушение → клиника заводит мероприятие», «методист публикует
этапы → клиника заказывает оплату → менеджер подтверждает → документ
открывается», «крупная оплата уходит во вторую руку, автор не может
подтвердить сам себя», «методист публикует годовой цикл → клиника настраивает
направление и собирает план → заводит оборудование и заполняет журнал →
грузит файл сводного отчёта → проводит самообследование, находит
несоответствие → оно САМО становится мероприятием → видно в дашборде панели» —
а не только «функция вернула true».

«Вторая рука» (SERVER.md §4) — единая точка на любую операцию: тип запроса
определяет, какое право нужно подтверждающему и что применить при подтверждении
(`container.secondHandHandlers`), поэтому `/api/second-hand/:id/confirm` один
на все семь операций, а не переписывается под каждую заново.

Матрица `ROLES` (`packages/shared/src/roles.ts`) перенесена дословно из
`reference/prototype/platform.js` — сервер проверяет ТУ ЖЕ матрицу, как того
требует `reference/CLAUDE.md`.

## Запуск локально

Требуется Node.js 20+, Docker (для Postgres), npm.

```bash
npm install
cp apps/api/.env.example apps/api/.env      # заполнить COOKIE_SECRET: openssl rand -hex 32
cp apps/web/.env.example apps/web/.env.local

docker compose -f infra/docker-compose.yml up -d   # только Postgres
npm run prisma:migrate                              # новая миграция после правки schema.prisma (начальная — prisma/migrations/0001_init)

npm run dev   # api на :4000, web на :3000
```

Откройте http://localhost:3000 — там ссылки на все кабинеты. Демо-аккаунтов
больше нет (`reference/SERVER.md` §7):

- **Клиника** (`/clinic`, `/executor`): `POST /api/auth/register` с `side=clinic`
  создаёт `clinic_admin` сразу (не заявка). Дальше в `/clinic` заведите
  сотрудников с ролями `vkk_lead`/`auditor` (регистрация с `role` в теле) и
  `nurse` с телефоном — для входа в `/executor`.
- **Платформа** — четыре самостоятельных кабинета на одной и той же общей
  реализации (`PanelShell.tsx`), различается только вход по роли:
  `/panel` (администратор), `/panel/methodist`, `/panel/manager`
  (менеджер по продажам), `/panel/head` (руководитель продаж).
  `POST /api/auth/register` с `side=operator` создаёт заявку (`pending`) —
  подтвердить некому, пока нет ни одного администратора. Первого создайте на
  сервере отдельной командой (см. «Деплой» ниже), локально — тем же скриптом
  через `npx tsx apps/api/src/scripts/createAdmin.ts --inn ... --login ... --password ...`.
- Каталоги (чек-листы, этапы, типы оборудования, сводный отчёт, годовой цикл)
  пусты, пока методист их не опубликует через `/panel/methodist` — либо накатите
  seed-скрипты (см. «Деплой»).

## Тесты и проверка

```bash
npm run typecheck   # все три пакета
npm test            # 285 тестов: shared (21) + api (264, включая HTTP-слой и все четыре кабинета)
npm run build       # shared → prisma generate → api → web
```

Все три команды сейчас проходят чисто — это гейт для `scripts/deploy.sh` и CI.

## Деплой на сервер (VPS по SSH)

```bash
cp infra/deploy/deploy.config.example.sh infra/deploy/deploy.config.sh
# заполнить DEPLOY_SSH_HOST/PORT/REMOTE_PATH

# на сервере один раз:
mkdir -p /opt/kontur785/shared
scp infra/deploy/.env.prod.example user@server:/opt/kontur785/shared/.env
# заполнить .env на сервере (COOKIE_SECRET, POSTGRES_PASSWORD, DOMAIN, ...)

./scripts/deploy.sh
```

`deploy.sh` — это то, что просили: **вносить изменения локально и переносить их
на рабочий развёрнутый сайт одной командой.** Схема — capistrano-style releases:

1. Локально прогоняются typecheck + тесты + сборка. Падает хоть один шаг —
   деплоя не будет, старая версия на сервере продолжает работать.
2. `rsync` копирует рабочую копию в `releases/<timestamp>` на сервере.
3. На сервере: `docker compose build`, `prisma migrate deploy`, `docker compose up -d`.
4. Проверка `/api/health`. Не прошла — симлинк `current` НЕ переключается,
   старый релиз как работал, так и работает (нулевой простой на неудачном деплое).
5. Успех — `current` переключается на новый релиз, старые релизы (кроме
   последних `DEPLOY_KEEP_RELEASES`) удаляются.

Откат без пересборки на любой сохранённый релиз: `./scripts/rollback.sh` (без
аргументов — список релизов), `./scripts/rollback.sh <id>` — откат.

Первый администратор платформы создаётся на сервере отдельной командой
(`reference/SERVER.md` §7, обязательная смена пароля при первом входе):

```bash
docker compose -f infra/docker-compose.prod.yml exec api \
  node dist/scripts/createAdmin.js --inn 7726345678 --login admin --password '<временный>' --fio "Фамилия И.О."
```

Начальные эталонные каталоги (SERVER.md §7 «эталонные справочники — как
начальные данные миграции»; все команды идемпотентны — не перезапишут то, что
уже опубликовал методист через `/panel`):

```bash
docker compose -f infra/docker-compose.prod.yml exec api node dist/scripts/seedChecklists.js
docker compose -f infra/docker-compose.prod.yml exec api node dist/scripts/seedStageDocs.js
docker compose -f infra/docker-compose.prod.yml exec api node dist/scripts/seedEquipTypes.js
docker compose -f infra/docker-compose.prod.yml exec api node dist/scripts/seedSummaryMaster.js
```

Годовой цикл (`cycle_master`) начальных данных не имеет — его публикует
методист через `/panel` (структура зависит от реальных направлений 785н
конкретной платформы).

## Что дальше (по приоритету, `reference/SERVER.md` §6)

Все семь операций «второй руки», тарифы, подписки, массовые операции с
откатом и финансовый дашборд — сделаны (см. таблицу выше и «Панель платформы»
ниже). Остаётся то, что осознанно не входит в перенос продукта, а в
инфраструктуру и внешние интеграции:

1. **Объектное хранилище файлов** — `LocalDiskFileStorage` (`apps/api/src/infra/files/`)
   держит фото и документы на диске сервера; порт (`FileStorage`) готов, замена
   на S3-совместимое хранилище — один новый адаптер, без изменений в вызывающих сервисах.
2. **Платёжный шлюз** — сейчас оплата этапа идёт только «по счёту» с ручным
   подтверждением оператором (`PaymentService`); эквайринг, автопродление —
   `reference/SERVER.md` §6.7. Подписки (`SubscriptionService`) продлеваются
   так же вручную — списание по тарифу не подключено.
3. **Хостинг в РФ + уведомление РКН** (152-ФЗ) — до продажи первой реальной
   клинике с персональными/медицинскими данными.
4. Чек-лист приёмки после переноса каждого экрана — `reference/SERVER.md` §9.

Закрыто с прошлого прохода аудита (было в этом списке, теперь работает по-настоящему):
провайдер SMS/email (`infra/providers/httpNotifier.ts` — SMS.ru/Resend, `.env`:
`SMS_PROVIDER_API_KEY`/`EMAIL_PROVIDER_API_KEY`/`EMAIL_FROM`), автоматическая
отправка дайджеста очереди работы по расписанию (`scheduler.ts`, раз в час,
не чаще раза в день — без внешнего cron), фоновые массовые операции больше
`SECOND_BULK` клиник (`BulkOperationService.applyFromSecondHand` заводит задачу
и возвращается сразу, прогресс — `GET /api/panel/bulk/jobs/:id`), генерация
DOCX/PDF документов и печать описи (`documents/render.ts`), подпись цепочки
журнала действий (`audit/chain.ts`, `AUDIT_LOG_SECRET`), изоляция доступа по
филиалу внутри клиники (`Account.branchName`, `rbac/service.ts` → `visibleToBranch`).

Закрыто следующим проходом: начальная миграция БД (`apps/api/prisma/migrations/0001_init`,
сгенерирована `prisma migrate diff` без живой БД — применить `prisma migrate deploy`);
напоминания и эскалация по срокам проверок и мероприятий (`clinic/reminderService.ts`:
за 3 дня — исполнителю, в день срока — исполнителю и руководству, просрочка — руководству;
получатель ищется по ФИО среди учётных записей клиники, повторов нет); показатель
готовности к проверке с раскладкой по причинам (`clinic/readinessService.ts`,
`GET /api/clinic/readiness`); акты обходов с номером `А-ГГГГ-NNN` и печатью в PDF;
порог `SECOND_BULK` считается накопительно по сотруднику за сутки; фоновые пачки,
прерванные перезапуском, помечаются ошибкой; принудительная смена временного пароля
(`mustChange` проверяет сервер); экраны смены роли сотрудника платформы, закрепления
сотрудника за филиалом и выбора филиала в плане и оборудовании.

Контур редакций стандарта (`apps/api/src/standard/editions.ts`): каждый из пяти каталогов
методиста (этапы, чек-листы, годовой цикл, типы оборудования, сводный отчёт) версионируется
отдельно. Публикация после подтверждения второй рукой выпускает НЕИЗМЕНЯЕМУЮ редакцию с
перечнем изменений; клиника работает по принятой ею редакции, новая приходит рекомендацией
(вкладка «Стандарт» в `/clinic`) — принять или остаться на прежней, решают админ клиники и
ответственный за ВКК. У методиста — вкладка «Внедрение стандарта» (кто на какой редакции,
кто отказался). Каталоги, опубликованные до введения версий, становятся редакцией 1, действующие
клиники остаются на ней. Пилотный тираж: публикация с `?pilot=ИНН,ИНН` (поле во вкладке
«Внедрение стандарта») даёт редакцию только выбранным клиникам, остальные не видят её и остаются
на прежней; «Выпустить для всех» (право публикации) делает её обычной рекомендацией. Откат: клиника
может вернуться на предыдущую редакцию («Стандарт» → «Вернуться на предыдущую»), новая при этом
помечается «отклонена» и не навязывается повторно. Собственный стандарт сети (`apps/api/src/network/`): сеть — несколько ИНН под головной клиникой; данные клиник
остаются изолированными, сеть лишь добавляет свой слой каталога. Сети и состав ведёт администратор платформы
(вкладка «Сети клиник», право `role:manage`), чек-листы сети — администратор ГОЛОВНОЙ клиники (вкладка «Сеть»,
право `org:write`); участницы видят их только для чтения. Слой накладывается в одной точке —
`StandardEditionService.catalog` — поэтому сетевые чек-листы появляются в самообследовании, обходах и годовом цикле.
Эталон главнее: одноимённый чек-лист сети отклоняется при сохранении, а если методист выпустил такой позже — скрывается
и помечается. Клиника состоит не более чем в одной сети. Изменения сети действуют сразу, без редакций и второй руки
(это стандарт организации, не эталон платформы). Пока слой — только чек-листы; документы этапов (цены, оплата, шаблоны)
и типы оборудования сеть не переопределяет. Хранится в платформенных каналах `networks` и `network_overlay:<id>`,
миграция БД не нужна.

Ещё закрыто: двухфактор в кабинетах (включение по паролю и коду из SMS/почты — включается только после

`npm run lint` проходит чисто и подключён в CI; заодно шрифты в `layout.tsx` переведены на
`next/font/google` вместо внешнего `<link>` на fonts.googleapis.com (самохостятся, без лишнего
запроса), внутренняя навигация — на `next/link` вместо `<a>`. Vitest поднят 2→5 (закрывает
CVE в `vite`/`esbuild`/`@vitest/mocker`, включая один critical), добавлен отчёт покрытия
(`apps/api/vitest.config.ts`, `npm run test:coverage --workspace apps/api`; пороги — с запасом
ниже фактических ~77/64/84/84%, ловят явную просадку). `.github/dependabot.yml` — еженедельные
апдейты npm и GitHub Actions. CI (`.github/workflows/ci.yml`) прогоняет `lint`, тесты с покрытием,
а также — сервисом Postgres — `prisma migrate deploy` по готовой миграции и дымовой сценарий
(`src/scripts/smokeCheckDb.ts`: регистрация → логин → сессия → логаут через Prisma-репозитории,
а не in-memory) — раньше миграция `0001_init` не проверялась ни разу на настоящей БД.
Не тронуто: постоянная уязвимость `postcss` (транзитивная через `next@15`, moderate/high) — фикс
только через мажорный next@16, не делал без отдельной браузерной регрессии на весь фронтенд;
эксплуатируется только при обработке недоверенного CSS, которого в проекте нет. Файловое
хранилище — по-прежнему `LocalDiskFileStorage` по умолчанию, но порт `FileStorage` теперь
умеет и S3 (`infra/files/s3FileStorage.ts`, любой S3-совместимый провайдер, не только AWS —
Selectel/Yandex Object Storage/VK Cloud для хостинга в РФ): переключается `FILES_DRIVER=s3` и
`FILES_S3_*` в `.env` (см. `.env.example`), код вызывающих сервисов не меняется.

«Ответственный менеджер» (`panel/managerAssignments.ts`) — администратор платформы закрепляет
менеджера по продажам за списком ИНН (вкладка «Ответственные менеджеры»); закреплённый менеджер
видит каталог клиентов, портфель и финансовую сводку только по своим клиникам и не может выдать
документ чужой. Сознательно НЕ включено по умолчанию: пока у менеджера нет ни одной записи в
этом канале, поведение прежнее (видит всех) — принудительное сужение всем сразу без миграции
данных мгновенно ослепило бы уже работающих менеджеров. `sales_head`/`platform_admin`/`methodist`
ограничению не подчиняются — они супервизоры с полным обзором. Не сужены: подписки, массовые
операции, напоминания и годовой цикл — те `tenants.listAll()`, что читаются для операций над
ВСЕЙ платформой (рассылка, годовой цикл, публикация редакций), а не для «какие клиники мои».

Сверка проекта с исходным продуктовым брифом (`reference/docs/*.dc.html` — аудит прототипа,
план развития по горизонтам, техаудит) закрыла ещё несколько пунктов:

- **Предиктор оттока по факту внедрения**, а не только по подписке (`DashboardService.isChurnRisk`,
  docs «План развития продукта» §8): клиника старше 30 дней и всё ещё не набравшая 40% готовности —
  риск, даже если подписка активна и далека от истечения.
- **Воронка привлечения** — из четырёх KPI брифа посчитаны ещё два: доля клиник, дошедших до
  первого завершённого обхода (`firstAuditRate`), и среднее число дней от регистрации клиники до
  первой выдачи документа (`avgDaysToFirstDocument`) — карточки в дашборде панели.
- **Автопродвижение пилота** (было — только ручная кнопка «Выпустить для всех»): у пилотной
  редакции теперь есть `pilotUntil` (срок — 7 дней от публикации, `standard/editions.ts`), и
  планировщик (`scheduler.ts`, раз в час) сам выпускает её для всех, если ни одна пилотная
  клиника не отказалась за это время; отказ («возражение») останавливает автовыпуск до ручного
  решения методиста. Панель показывает срок рядом со списком пилотных клиник.
- **Файлы с контрольной суммой** (docs «Горизонт 1»: сущность `FileObject`) — порт `FileStorage`
  считает sha256 при сохранении во всех трёх адаптерах (память/диск/S3) и возвращает его при
  чтении; показывается клинике при загрузке сводного отчёта (первые 16 знаков с подсказкой) и
  в тексте акта обхода рядом с фото находки. Версионирования файлов (несколько версий одного
  логического файла) всё ещё нет — при повторной загрузке новый файл просто получает новый id.
- **Простая электронная подпись акта** (docs «Горизонт 1»: сущность `Signature`, «в этом
  горизонте — простая, с задела под УКЭП»): при завершении обхода акт фиксирует, кто его завершил,
  когда (с точностью до минуты) и sha256 пунктов на тот момент — это печатается в PDF вместо
  пустой строки «Проверяющий: ______». Повторное завершение (офлайн-ретрай) подпись не переписывает.
  Вторая строка акта, «Ответственный за ВКК», остаётся ручной — это подпись другого человека,
  не автоматизирована. Настоящей УКЭП (усиленной квалифицированной) это не заменяет.
- **Мобильный обход как PWA** (docs «План развития продукта» §5, горизонт 2) — манифест и
  сервис-воркер только на `/walk` (`apps/web/public/manifest.webmanifest`, `public/sw.js`,
  `walk/layout.tsx`), устанавливается на экран телефона. Сервис-воркер сознательно ничего не
  кэширует — офлайн-очередь обхода и так устроена в `localStorage`, а кэшировать ответы API в
  надзорном продукте опаснее, чем не иметь кэша (устаревшие данные выглядели бы как настоящие);
  push-напоминаний о плановых проверках нет.
- Не сделано из той же сверки (осталось для будущего прохода): версии файлов (не только
  контрольная сумма), УКЭП поверх простой подписи, кабинет управляющей компании сети (сравнение
  объектов, рейтинг, повторяющиеся нарушения по сети — сама сеть пока даёт только общий слой
  чек-листов), интеграция с МИС, обучение и аттестация персонала.

## Панель платформы: тарифы, подписки, массовые операции

Функционал ниже одинаков во всех четырёх кабинетах платформы (`/panel`,
`/panel/methodist`, `/panel/manager`, `/panel/head`) — это одна реализация
(`apps/web/src/app/panel/PanelShell.tsx`), кабинеты различаются только тем,
чья роль допускается ко входу; какие вкладки реально что-то делают, а не
просто отображают чужие данные для чтения, — решают права роли (`can()`
из `packages/shared/src/roles.ts`), проверенные и на сервере, и на фронтенде
одинаково для всех четырёх точек входа.

- **Тарифы** (`TariffService`, вкладка «Тарифы»): черновик (`tariff:write` —
  менеджер, руководитель продаж, администратор) правится напрямую; включение в
  продажу и удаление уже опубликованного — каждое отдельный запрос второй руки
  (`tariff:publish`/`tariff:delete`), подтверждает другой сотрудник с
  `second:money`. Методист тарифов не касается — у него нет `tariff:write`.
- **Подписки** (`SubscriptionService`, вкладка «Подписки»): менеджер/
  руководитель продаж/администратор назначают тариф клинике, продлевают и
  отменяют (`sub:write`) — прямое действие, не входит в семь операций второй
  руки. Список — вкладка «Подписки», статус клиники также виден в «Дашборд и
  клиенты».
- **Массовые операции** (`BulkOperationService`, вкладка «Массовые операции»):
  предпроверка каждой клиники → предпросмотр эффекта и суммы → применение
  (пачка больше `SECOND_BULK`=20 клиник — через вторую руку `bulk:clinics`,
  право подтверждающего зависит от вида пачки: методология — `second:standard`,
  деньги — `second:money`) → отчёт по каждой клинике (применилось/пропущено/
  ошибка) → «Откатить операцию» по снимку затронутых каналов ДО записи.
  Встроенные операции: продление подписки (+30 дней, с откатом), напоминание
  об оплате (без изменения данных, без отката — см. «Что дальше»), применение
  годового цикла эталона ко всем отмеченным клиникам разом (с откатом).
  Добавить новую операцию — это запись в `BULK_ACTIONS` (`container.ts`), не
  правка движка.
- **Финансовый дашборд** (`DashboardService.getFinancials`, вкладка «Дашборд и
  клиенты»): MRR (годовые тарифы — по месячному эквиваленту), ARPA, отток
  (доля отменённых/истёкших подписок), востребованность тарифов, средний срок
  внедрения (от заказа первого этапа до приёмки последнего принятого).
- **Выдача документа без оплаты** (`doc:grant-without-payment`): вместо
  прямой записи (`POST /api/documents/grant` с `paid:false`) заводится запрос
  второй руки, подтверждает другой сотрудник с `doc:grant`; выдающим в записи
  становится ПОДТВЕРЖДАЮЩИЙ, не автор запроса.
- **Публикация эталонов** (`standard:publish` — чек-листы, этапы, годовой
  цикл, типы оборудования, сводный отчёт): теперь тоже через вторую руку —
  методист/администратор заводит запрос, ДРУГОЙ методист/администратор
  подтверждает. Раньше публиковалось сразу же по нажатию — это было
  расхождение с SERVER.md §4, исправлено вместе с остальными операциями.
- **Очередь работы** (`WorkQueueService`, вкладка «Очередь работы»,
  reference/prototype/Админ-панель.dc.html «Очередь работы»): список задач
  НЕ хранится — пересчитывается из реальных данных при каждом чтении (счёт
  не оплачен больше 3 дней, подписка истекла без продления, клиника без
  единого обхода); хранится только состояние работы над задачей (взял в
  работу / отложил / закрыл) — общее для всех операторов, «одну клинику не
  обзвонят дважды». Отложенная возвращается через 3 дня, закрытая — на
  следующий день, если причина не исчезла. Право на всё — `clinic:read`
  (есть у всех четырёх ролей платформы, очередь общая, не привязана к роли).
  Дайджест по кнопке — см. «Что дальше» п.1.
- **Каталог клиентов** (`DashboardService.listClients`/`getPortfolio`,
  вкладка «Дашборд и клиенты»): фильтры «Все / Trial / Риск оттока / Сети с
  филиалами», готовность клиники (% выданных документов от каталога),
  активность (последний вход сотрудника клиники), карточки «Портфель»
  (клиник на платформе, MRR, средняя готовность, обходов за выбранный
  период — 7/30/90 дней), «+ Добавить клинику» (`sub:write` — заводит
  тенант и администратора клиники напрямую, минуя саморегистрацию) и
  «Выгрузить отчёт» (CSV).

## Известные ограничения (говорим прямо, не прячем)

- Все четыре кабинета на фронтенде — клиентские компоненты (`'use client'`):
  до гидратации страница пустая (нет SSR данных сессии). Стоит рассмотреть
  серверные компоненты с чтением cookie на сервере.
- «Сотрудники и матрица ответственных» в `/clinic` — упрощённая версия
  прототипа: матрица назначает ответственного на ПРОИЗВОЛЬНОЕ имя документа
  (текстом), а не на привязанный каталог направлений 785н; без учёта обучения
  по ИСМП и статуса «уволен».
- «Каталог этапов», «Годовой цикл», «Типы оборудования» и «Сводный отчёт» в
  `/panel` — полноценные вложенные формы (`apps/web/src/app/panel/catalogForms.tsx`),
  без ручного JSON; публикуют тот же объект, что раньше собирался вручную.
- Разбор годового цикла (`CycleService.generatePlan`) заменяет строки плана с
  префиксом `cyc-` целиком при каждой генерации — правки клиники внутри
  сгенерированной строки (кроме донастройки самого направления) не сохранятся
  при повторной генерации; ручные записи `PlanService` не трогает.
- Разбивка документов прототипа (блоки `b01`–`b09`, реальные названия из
  `reference/prototype/Личный кабинет ВКК.dc.html`) по этапам 1–4 в
  `seedStageDocs.ts`, типы оборудования в `seedEquipTypes.ts` — самостоятельная
  реконструкция по смыслу продукта, а не проверенная копия внутренней связки
  прототипа (`blocks_catalog`/`doc_catalogs`/`block_tpls`/`equip_types`),
  которая слишком плотно завязана на структуры, не перенесённые буквально.
  Состав сводного отчёта (`seedSummaryMaster.ts`) и три эталонных чек-листа
  (`seedChecklists.ts`) — исключение, это дословные строки из прототипа.
  Это касается только СОДЕРЖАНИЯ (какой документ лежит в каком этапе) — сам
  МЕХАНИЗМ уже не декоративный: `StageService` (`apps/api/src/clinic/stageService.ts`)
  требует, чтобы этапы шли строго по порядку кода — заказать оплату этапа N
  нельзя, пока этап N−1 не оплачен И не принят платформой отдельным действием
  «приёмка» (`POST /api/panel/stage-payments/:inn/:code/accept`, право
  `doc:grant` — методист/менеджер/руководитель продаж/администратор). Оплата
  подтверждается продавцом (`money:write`), приёмка — методистом/платформой
  (`doc:grant`); это разные факты, разные роли, обе стороны видны в кабинете
  клиники (`/clinic`, статус «оплачен · ждёт приёмки платформой») и панели
  (`/panel` → «Оплата этапов» → «Принять этап»). Покрыто тестами
  (`stageService.test.ts`, блок «последовательная блокировка этапов и приёмка
  платформой»; `http/app.test.ts`).
- В прототипе обещано, что при завершении обхода «система создаст... план
  CAPA» — на деле в прототипе этого кода нет (проверено: находки не пишутся
  никуда, кроме текста экрана). Перенесено то, что реально работает: клиника
  видит находки и превращает их в мероприятие вручную. Для самообследования
  автоматика реализована по-настоящему (`SelfAuditService.finish`) — там её
  проводит тот же сотрудник, который держит право `capa:write`, так что
  привилегия не эскалируется (см. комментарий в коде).
- Оплата этапа — только «по счёту» с ручным подтверждением оператором;
  реального эквайринга нет (см. «Что дальше», п.4).
- **Профиль клиники** (`ProfileService`, вкладка «Профиль клиники» в `/clinic`)
  — реквизиты (наименование, лицензия, руководитель, город), подставляются в
  шаблоны документов (`{{org}}`, `{{license}}`, `{{chief_doctor}}`, `{{city}}`).
  Без адреса, логотипа и «видов работ» — это уже часть филиалов
  (`reference/prototype/Личный кабинет ВКК.dc.html`: `branches`/`svcRows`),
  которые в перенесённой модели — просто `{id, name}`.
- **Оффер этапа** (`Stage.offerText`/`offerFile`, `StagePaymentState.offerAccepted`)
  — методист может приложить текст условий к этапу в каталоге; если условия
  есть, клиника обязана явно принять их, прежде чем заказать оплату. Файл
  оффера — только имя файла (текстовое поле в форме методиста), реальной
  загрузки/хранения PDF нет — это было бы отдельной интеграцией с объектным
  хранилищем сверх того, что попросили.
- **Опись документов** (`InventoryService`, вкладка «Опись документов» в
  `/clinic`) — сводный контрольный лист по документам этапов и сводного
  отчёта с фильтром «не заполнено». Осознанно НЕ показывает «редакцию
  документа» и «эталон vs добавлено клиникой», как в прототипе
  (`docInventory()`) — этих полей нет ни у одного документа в перенесённой
  модели (`DocumentGrantRow` не хранит номер редакции), и подделывать их
  значило бы показывать недостоверные данные.
- Оборудование: формы через `/clinic` заполняются только текстовым
  значением/примечанием (`value`/`note`) — построчный ответ по пунктам чек-листа
  (`answers`) поддержан на бэкенде (`EquipmentService.fillForm`), но не в UI.
- Офлайн-очередь обхода (`apps/web/src/app/walk/page.tsx`) хранится в
  `localStorage` одним общим ключом на вкладку — этого достаточно для
  «потерял сеть на минуту в кабинете», но не для многодневной работы без
  связи на нескольких устройствах одновременно. Идемпотентность на сервере
  (`opId`) готова к более надёжной очереди (IndexedDB + Background Sync).
- Изоляция по филиалу не доходит до агрегатов: показатель готовности, напоминания и дашборд платформы считают клинику целиком; сотруднику филиала они не раскрывают состав чужих находок, но числа общие.
- Каталог клиентов в панели читает данные по одному чтению каналов на клинику
  (N+1) — приемлемо для десятков клиник, для сотен нужен агрегирующий
  материал вместо чтения `staff`/`stage_paid`/`capa` на лету (см. `DashboardService`).
- Адаптивность под устройства проверена в реальном браузере (Playwright) на 390/820/1440 px —
  все кабинеты (`/clinic`, `/panel`, `/panel/methodist`, `/panel/manager`, `/panel/head`,
  `/executor`, `/walk`), их вкладки, диалоги (2FA, смена пароля, просмотр документа) и экраны
  входа/регистрации/сброса/приглашения; проверка — отсутствие горизонтальной прокрутки
  страницы (`scrollWidth` vs `clientWidth`), не только факт отдачи 200. По итогам поправлены
  несколько строк с `<select>` без `flexWrap` (запрос смены роли, подтверждение заявки,
  кнопки публикации каталогов), где длинный текст опции раздвигал строку шире экрана.
  Явный `viewport` в `layout.tsx` (`viewportFit: 'cover'`) и `env(safe-area-inset-bottom)`
  на нижней панели обхода (`/walk`) — под чёлку и жестовую полосу iPhone. Точечная визуальная
  (не только «не течёт») сверка с прототипом пиксель-в-пиксель не проводилась — при желании
  показать дизайнеру для придирчивой сверки, сделайте её отдельно.
- Единственный настоящий e2e прогон — HTTP-уровень (`apps/api/src/http/app.test.ts`),
  не браузерный. Playwright/Cypress ещё не подключены.
- Порог `SECOND_BULK` (массовая операция больше 20 клиник — вторая рука) можно
  обойти, разбив одну операцию на несколько вызовов `commit` по ≤20 клиник —
  сервер не отслеживает накопление по времени/актёру. Тот же порог в
  прототипе (`reference/prototype/Админ-панель.dc.html`, `bulkCommit`) —
  чисто клиентский софт-порог и обходится ровно так же; ужесточение требует
  новой инфраструктуры (rate-limit/накопительный счётчик), которой в проекте
  пока нет нигде.
- «Ответственный менеджер» — закрепление конкретного сотрудника платформы за
  клиникой с ограничением его доступа только своими клиниками (SERVER.md §4)
  не реализовано: любой сотрудник с правом `doc:grant`/`clinic:read` видит и
  выдаёт документы по всем клиникам, а не только по «своим». Это отдельная
  модель данных (закрепление менеджер↔клиника плюс фильтрация во всех местах,
  где сейчас читается `tenants.listAll()`), не однострочная правка.
