# Контур 785

SaaS для внутреннего контроля качества и безопасности медицинской деятельности
(Приказ Минздрава №785н). Продакшн-реализация прототипа из `reference/`
(`reference/README.md` — продукт и дизайн-токены, `reference/SERVER.md` —
архитектура переноса, `reference/CLAUDE.md` — неизменные правила продукта).

## Статус переноса

Перенос идёт по порядку из `reference/SERVER.md` §6: исполнитель → обход →
клиника → панель. Инфраструктура и общая логика (auth, RBAC, журнал действий,
вторая рука, выдача документов) — фундамент для ВСЕХ кабинетов и уже полностью
готовы и покрыты тестами.

| Слой | Статус |
|---|---|
| Схема БД (`apps/api/prisma/schema.prisma`) | готово |
| Аутентификация: пароль (argon2), 2FA, сброс пароля, сессии в БД | готово |
| RBAC — матрица `ROLES` проверяется на каждом эндпоинте | готово |
| Журнал действий (append-only, включая отказы) | готово |
| «Вторая рука» — движок + повышение роли | готово (движок общий, остальные 6 операций — по мере переноса экранов) |
| Выдача документов клинике (grant/revoke, версии) | готово |
| Версионированные каналы данных + идемпотентность по `opId` | готово |
| Объектное хранилище файлов (фото-доказательства) | готово, адаптер — локальный диск (см. «Что дальше») |
| **Кабинет исполнителя** | **готово end-to-end** (API + UI, `/executor`) |
| **Мобильный обход** | **готово end-to-end для «Аудитов»** (API + UI, `/walk`, офлайн-очередь). «Оборудование» и «Сводный отчёт» — не перенесены |
| **Личный кабинет ВКК** | **готово для «Сотрудники», «План проверок», «Находки и CAPA»** (API + UI, `/clinic`). Этапы внедрения, документы, годовой цикл, оборудование, самообследование — не перенесены |
| Панель платформы (админ/методист/менеджер/рук. продаж) | не перенесена — заглушка `/panel` |
| Docker / деплой на VPS / rollback | готово |
| CI (typecheck + тесты + сборка) | готово (`.github/workflows/ci.yml`) |

Заглушка `/panel` уже проверяет сессию и роль по-настоящему (не бутафория) —
просто не показывает перенесённый экран. См.
`apps/web/src/components/InProgressCabinet.tsx`.

**Не готово к продаже прямо сейчас** — честно, по `reference/SERVER.md` §7:
провайдер SMS/email (сейчас коды 2FA и сброса пароля уходят в лог сервера,
`ConsoleNotifier`), платёжный шлюз, хостинг в РФ + уведомление РКН (152-ФЗ),
и панель платформы. Список — раздел «Что дальше» ниже.

## Архитектура

```
kontur785/
├── reference/          # исходный прототип — эталон вида/поведения, не трогать
├── packages/shared/    # ROLES, права, ИНН/телефон/пароль-валидация — общий источник правды
├── apps/api/           # Fastify + Prisma + PostgreSQL
│   ├── src/domain/     # порты (интерфейсы репозиториев) и типы — hexagonal architecture
│   ├── src/infra/memory/   # in-memory адаптеры — для тестов, без БД
│   ├── src/infra/prisma/   # Postgres-адаптеры — для прод
│   ├── src/auth/        src/rbac/        src/secondHand/
│   ├── src/documents/   src/executor/    src/walk/        src/http/routes/
│   ├── src/clinic/      # штат, план проверок, CAPA (staffService/planService/capaService)
│   ├── src/shared/      # общая логика чтения каналов (assignment.ts, channelShapes.ts) — исполнитель, обход и клиника читают одни и те же audit_plan/staff/docasg
│   └── prisma/schema.prisma, hardening.sql
├── apps/web/            # Next.js (App Router, TypeScript)
│   ├── src/app/executor/page.tsx   # готовый кабинет исполнителя
│   ├── src/app/walk/page.tsx       # готовый мобильный обход (аудиты) с офлайн-очередью
│   └── src/app/clinic/page.tsx     # готовый Личный кабинет ВКК (штат, план, CAPA)
└── infra/               # docker-compose (dev/prod), Caddyfile, deploy/
```

Сервисы (`AuthService`, `SecondHandService`, `DocumentService`, `ExecutorService`,
`WalkService`, `StaffService`, `PlanService`, `CapaService`) работают через порты
(`domain/ports.ts`) и не знают, что за ними — Postgres или память. Это не
архитектурная мода: именно поэтому у нас **121 честный тест** (shared 21 + api 100),
которые гоняются без поднятой базы данных за секунды, и HTTP-интеграционные тесты
(`src/http/app.test.ts`), проверяющие реальные cookie-сессии, 401/403 и полную
цепочку «клиника заводит проверку → обход её проводит и находит нарушение →
клиника превращает находку в мероприятие» — а не только «функция вернула true».

Матрица `ROLES` (`packages/shared/src/roles.ts`) перенесена дословно из
`reference/prototype/platform.js` — сервер проверяет ТУ ЖЕ матрицу, как того
требует `reference/CLAUDE.md`.

## Запуск локально

Требуется Node.js 20+, Docker (для Postgres), npm.

```bash
npm install
cp apps/api/.env.example apps/api/.env      # заполнить COOKIE_SECRET: openssl rand -hex 32
cp apps/web/.env.example apps/web/.env.local

docker compose -f infra/docker-compose.yml up -d   # только Postgres
npm run prisma:migrate                              # первая миграция схемы

npm run dev   # api на :4000, web на :3000
```

Откройте http://localhost:3000 — там ссылки на все готовые кабинеты. Демо-аккаунтов
больше нет (`reference/SERVER.md` §7) — зарегистрируйте клинику через
`POST /api/auth/register` (side=clinic, роль по умолчанию `clinic_admin`) и
войдите в `/clinic` по ИНН+логину+паролю. Там же заведите сотрудника с ролью
`vkk_lead` или `auditor` (регистрация с `role` в теле запроса) и `nurse` с
телефоном — для входа в `/executor`.

## Тесты и проверка

```bash
npm run typecheck   # все три пакета
npm test            # 121 тест: shared (21) + api (100, включая HTTP-слой, обход и клинику)
npm run build       # shared → prisma generate → api → web
```

Все три команды сейчас проходят чисто — это гейт для `scripts/deploy.sh` и CI.

## Деплой на сервер (VPS по SSH)

```bash
cp infra/deploy/deploy.config.example.sh infra/deploy/deploy.config.sh
# заполнить DEPLOY_SSH_HOST/PORT/REMOTE_PATH

# на сервере один раз:
mkdir -p /opt/kontur785/shared
scp infra/deploy/.env.prod.example user@server:/opt/kontur785/shared/.env
# заполнить .env на сервере (COOKIE_SECRET, POSTGRES_PASSWORD, DOMAIN, ...)

./scripts/deploy.sh
```

`deploy.sh` — это то, что просили: **вносить изменения локально и переносить их
на рабочий развёрнутый сайт одной командой.** Схема — capistrano-style releases:

1. Локально прогоняются typecheck + тесты + сборка. Падает хоть один шаг —
   деплоя не будет, старая версия на сервере продолжает работать.
2. `rsync` копирует рабочую копию в `releases/<timestamp>` на сервере.
3. На сервере: `docker compose build`, `prisma migrate deploy`, `docker compose up -d`.
4. Проверка `/api/health`. Не прошла — симлинк `current` НЕ переключается,
   старый релиз как работал, так и работает (нулевой простой на неудачном деплое).
5. Успех — `current` переключается на новый релиз, старые релизы (кроме
   последних `DEPLOY_KEEP_RELEASES`) удаляются.

Откат без пересборки на любой сохранённый релиз: `./scripts/rollback.sh` (без
аргументов — список релизов), `./scripts/rollback.sh <id>` — откат.

Первый администратор платформы создаётся на сервере отдельной командой
(`reference/SERVER.md` §7, обязательная смена пароля при первом входе):

```bash
docker compose -f infra/docker-compose.prod.yml exec api \
  node dist/scripts/createAdmin.js --inn 7726345678 --login admin --password '<временный>' --fio "Фамилия И.О."
```

Каталог чек-листов (методист ещё не перенесён — панель не готова публиковать
свои): начальные три эталонных чек-листа 785н переносятся отдельной командой
(`reference/SERVER.md` §7 «эталонные справочники — как начальные данные миграции»,
идемпотентна — не перезапишет то, что уже опубликовано):

```bash
docker compose -f infra/docker-compose.prod.yml exec api node dist/scripts/seedChecklists.js
```

## Что дальше (по приоритету, `reference/SERVER.md` §6)

1. **Этапы внедрения и документы** в Личном кабинете ВКК — самая большая
   оставшаяся часть экрана (10 400 строк прототипа): состав документов по
   этапам, выдача (уже готова на бэкенде — `DocumentService`/`/api/documents/*`,
   не хватает только экрана клиники, который её показывает), опись документов.
2. **Годовой цикл** — эталон методиста (`cycle_master`) + его разбор клиникой
   в помесячный план проверок (`cycle_live`). Пока не перенесён, `PlanService`
   покрывает только ручные записи плана — этого достаточно для реальной
   работы, но не для авто-генерации проверок на год вперёд.
3. **Панель платформы** (`/panel`) — включая публикацию каталога чек-листов
   методистом (сейчас это делает `seedChecklists.js` вручную), годового цикла,
   и пять оставшихся операций «второй руки» (публикация эталона/тарифов,
   удаление тарифа, массовая операция, подтверждение крупной оплаты, выдача
   без оплаты) — движок уже готов (`SecondHandService`), нужно вызвать
   `request(...)` из нужных экранов панели.
4. **Оборудование и «Сводный отчёт»** в мобильном обходе — читаются исполнителем
   уже сейчас (`equip_pos`/`equip_fill`), но запись через сам экран обхода не
   перенесена: она завязана на годовой цикл (п.2).
5. **Провайдер SMS/email** — заменить `ConsoleNotifier` (`apps/api/src/infra/memory/notifier.ts`)
   на реальный шлюз (см. `.env.example`: `SMS_PROVIDER_API_KEY`, `EMAIL_PROVIDER_API_KEY`).
6. **Объектное хранилище файлов** — `LocalDiskFileStorage` (`apps/api/src/infra/files/`)
   держит фото обхода на диске сервера; порт (`FileStorage`) готов, замена на
   S3-совместимое хранилище — один новый адаптер, без изменений в `WalkService`.
7. **Платёжный шлюз** — эквайринг, счёт-оферта, автопродление (`reference/SERVER.md` §6.7).
8. **Хостинг в РФ + уведомление РКН** (152-ФЗ) — до продажи первой реальной
   клинике с персональными/медицинскими данными.
9. Чек-лист приёмки после переноса каждого экрана — `reference/SERVER.md` §9.

## Известные ограничения (говорим прямо, не прячем)

- `mustChange` (обязательная смена пароля после `createAdmin`/`adminSetPassword`)
  сейчас только возвращается в `/api/auth/session` — фронтенд должен сам
  показать экран смены пароля и не пускать дальше; сервер пока не блокирует
  остальные эндпоинты по этому флагу. Добавить перед первым реальным клиентом.
- Кабинеты исполнителя, обхода и клиники на фронтенде — клиентские компоненты
  (`'use client'`): до гидратации страница пустая (нет SSR данных сессии). Для
  остальных экранов стоит рассмотреть серверные компоненты с чтением cookie
  на сервере.
- «Сотрудники и матрица ответственных» в `/clinic` — упрощённая версия
  прототипа: без филиалов, учёта обучения по ИСМП и статуса «уволен»; матрица
  назначает ответственного на ПРОИЗВОЛЬНОЕ имя документа (текстом), а не на
  привязанный каталог направлений 785н — тот каталог публикует методист,
  которого ещё нет. «План проверок» переносит только ручные записи, не
  авто-генерацию из годового цикла (см. «Что дальше», п.2).
- В прототипе обещано, что при завершении обхода «система создаст... план
  CAPA» — на деле в прототипе этого кода нет (проверено: находки не пишутся
  никуда, кроме текста экрана). Перенесено то, что реально работает: клиника
  видит находки и превращает их в мероприятие вручную (`POST /api/clinic/capa`,
  раздел «Находки» в `/clinic`) — не выдуманная автоматика, а рабочий цикл.
- Офлайн-очередь обхода (`apps/web/src/app/walk/page.tsx`) хранится в
  `localStorage` одним общим ключом на вкладку — этого достаточно для
  «потерял сеть на минуту в кабинете», но не для многодневной работы без
  связи на нескольких устройствах одновременно. Идемпотентность на сервере
  (`opId`) готова к более надёжной очереди (IndexedDB + Background Sync),
  когда она понадобится.
- «Вторая рука» для выдачи документа без оплаты (`doc:grant-without-payment`)
  сейчас у `/api/documents/grant` просто отклоняется с подсказкой оформить
  через `/api/second-hand/request` — сам вызов `request(...)` с этим типом
  из экрана карточки клиники ещё не добавлен (экран не перенесён).
- Визуальная сверка с прототипом на 390/820/1440 px (`reference/CLAUDE.md`)
  не выполнялась в реальном браузере в рамках этой сессии — только
  `next build` и HTTP-смоук (страницы отдают 200, вёрстка не проверена глазами).
  Сделайте её перед показом клиенту.
- Единственный настоящий e2e прогон — HTTP-уровень (`apps/api/src/http/app.test.ts`),
  не браузерный. Playwright/Cypress ещё не подключены.
