# Контур 785

SaaS для внутреннего контроля качества и безопасности медицинской деятельности
(Приказ Минздрава №785н). Продакшн-реализация прототипа из `reference/`
(`reference/README.md` — продукт и дизайн-токены, `reference/SERVER.md` —
архитектура переноса, `reference/CLAUDE.md` — неизменные правила продукта).

## Статус переноса

Перенос идёт по порядку из `reference/SERVER.md` §6: исполнитель → обход →
клиника → панель. Все четыре кабинета из этого порядка сейчас в рабочем
состоянии (не заглушки), но не на 100% — каждый охватывает свою основную
бизнес-логику, а второстепенные разделы (годовой цикл, филиалы, тарифы,
каталог клиентов) перенесены в следующий заход. Инфраструктура и общая логика
(auth, RBAC, журнал действий, вторая рука, выдача документов) — фундамент для
всех кабинетов — готовы полностью.

| Слой | Статус |
|---|---|
| Схема БД (`apps/api/prisma/schema.prisma`) | готово |
| Аутентификация: пароль (argon2), 2FA, сброс пароля, сессии в БД | готово |
| RBAC — матрица `ROLES` проверяется на каждом эндпоинте | готово |
| Журнал действий (append-only, включая отказы) | готово |
| «Вторая рука» — единый движок для ЛЮБОЙ операции по типу запроса | готово: повышение роли, подтверждение крупной оплаты; остальные 5 — по мере переноса нужных экранов |
| Выдача документов клинике (grant/revoke, версии) | готово |
| Версионированные каналы данных + идемпотентность по `opId` | готово |
| Объектное хранилище файлов (фото-доказательства) | готово, адаптер — локальный диск (см. «Что дальше») |
| **Кабинет исполнителя** | **готово end-to-end** (API + UI, `/executor`) |
| **Мобильный обход** | **готово для «Аудитов»** (API + UI, `/walk`, офлайн-очередь). «Оборудование» и «Сводный отчёт» — не перенесены |
| **Личный кабинет ВКК** | **готово**: этапы внедрения и документы с оплатой, сотрудники и матрица ответственных, план проверок, находки → CAPA (API + UI, `/clinic`). Годовой цикл, филиалы, самообследование — не перенесены |
| **Панель платформы** | **готово**: публикация чек-листов/этапов/годового цикла методистом, подтверждение оплаты, заявки на доступ, вторая рука (API + UI, `/panel`). Дашборд, каталог клиентов, подписки, тарифы — не перенесены |
| Docker / деплой на VPS / rollback | готово |
| CI (typecheck + тесты + сборка) | готово (`.github/workflows/ci.yml`) |

**Не готово к продаже прямо сейчас** — честно, по `reference/SERVER.md` §7:
провайдер SMS/email (сейчас коды 2FA и сброса пароля уходят в лог сервера,
`ConsoleNotifier`), платёжный шлюз (оплата этапа сейчас — счёт с ручным
подтверждением оператором, без эквайринга), хостинг в РФ + уведомление РКН
(152-ФЗ). Список полностью — раздел «Что дальше» ниже.

```
kontur785/

├── packages/shared/    # ROLES, права, ИНН/телефон/пароль-валидация — общий источник правды
├── apps/api/           # Fastify + Prisma + PostgreSQL
│   ├── src/domain/     # порты (интерфейсы репозиториев) и типы — hexagonal architecture
│   ├── src/infra/memory/   # in-memory адаптеры — для тестов, без БД
│   ├── src/infra/prisma/   # Postgres-адаптеры — для прод
│   ├── src/auth/        src/rbac/        src/secondHand/    src/http/routes/
│   ├── src/documents/   src/executor/    src/walk/
│   ├── src/clinic/      # штат, план проверок, CAPA, этапы и документы клиники
│   ├── src/panel/       # публикация эталонов методистом, подтверждение оплаты
│   ├── src/shared/      # общая логика чтения каналов (assignment.ts, channelShapes.ts) — исполнитель, обход, клиника и панель читают одни и те же audit_plan/staff/docasg/stage_docs
│   └── prisma/schema.prisma, hardening.sql
├── apps/web/            # Next.js (App Router, TypeScript)
│   ├── src/app/executor/page.tsx   # кабинет исполнителя
│   ├── src/app/walk/page.tsx       # мобильный обход (аудиты) с офлайн-очередью
│   ├── src/app/clinic/page.tsx     # Личный кабинет ВКК
│   └── src/app/panel/page.tsx      # панель платформы
└── infra/               # docker-compose (dev/prod), Caddyfile, deploy/
```

Сервисы (`AuthService`, `SecondHandService`, `DocumentService`, `ExecutorService`,
`WalkService`, `StaffService`, `PlanService`, `CapaService`, `StageService`,
`CatalogService`, `PaymentService`) работают через порты (`domain/ports.ts`) и
не знают, что за ними — Postgres или память. Это не архитектурная мода: именно
поэтому у нас **145 честных тестов** (shared 21 + api 124), которые гоняются
без поднятой базы данных за секунды, и HTTP-интеграционные тесты
(`src/http/app.test.ts`), проверяющие реальные cookie-сессии, 401/403 и полные
цепочки продукта — «клиника заводит проверку → обход находит нарушение →
клиника заводит мероприятие», «методист публикует этапы → клиника заказывает
оплату → менеджер подтверждает → документ открывается», «крупная оплата уходит
во вторую руку, автор не может подтвердить сам себя» — а не только «функция
вернула true».

«Вторая рука» (SERVER.md §4) — единая точка на любую операцию: тип запроса
определяет, какое право нужно подтверждающему и что применить при подтверждении
(`container.secondHandHandlers`), поэтому `/api/second-hand/:id/confirm` один
на все семь операций, а не переписывается под каждую заново.

Матрица `ROLES` (`packages/shared/src/roles.ts`) перенесена дословно из
`reference/prototype/platform.js` — сервер проверяет ТУ ЖЕ матрицу, как того
требует `reference/CLAUDE.md`.

## Запуск локально

Требуется Node.js 20+, Docker (для Postgres), npm.

```bash
npm install
cp apps/api/.env.example apps/api/.env      # заполнить COOKIE_SECRET: openssl rand -hex 32
cp apps/web/.env.example apps/web/.env.local

docker compose -f infra/docker-compose.yml up -d   # только Postgres
npm run prisma:migrate                              # первая миграция схемы

npm run dev   # api на :4000, web на :3000
```

Откройте http://localhost:3000 — там ссылки на все четыре кабинета. Демо-аккаунтов
больше нет (`reference/SERVER.md` §7):

- **Клиника** (`/clinic`, `/executor`): `POST /api/auth/register` с `side=clinic`
  создаёт `clinic_admin` сразу (не заявка). Дальше в `/clinic` заведите
  сотрудников с ролями `vkk_lead`/`auditor` (регистрация с `role` в теле) и
  `nurse` с телефоном — для входа в `/executor`.
- **Платформа** (`/panel`): `POST /api/auth/register` с `side=operator` создаёт
  заявку (`pending`) — подтвердить некому, пока нет ни одного администратора.
  Первого создайте на сервере отдельной командой (см. «Деплой» ниже), локально —
  тем же скриптом через `npx tsx apps/api/src/scripts/createAdmin.ts --inn ... --login ... --password ...`.
- Каталог чек-листов и этапов пуст, пока методист (или скрипты `seedChecklists`/
  `seedStageDocs`, см. «Деплой») их не опубликует — без этого `/clinic` покажет
  пустые списки, это ожидаемо.

## Тесты и проверка

```bash
npm run typecheck   # все три пакета
npm test            # 145 тестов: shared (21) + api (124, включая HTTP-слой, обход, клинику и панель)
npm run build       # shared → prisma generate → api → web
```

Все три команды сейчас проходят чисто — это гейт для `scripts/deploy.sh` и CI.

## Деплой на сервер (VPS по SSH)

```bash
cp infra/deploy/deploy.config.example.sh infra/deploy/deploy.config.sh
# заполнить DEPLOY_SSH_HOST/PORT/REMOTE_PATH

# на сервере один раз:
mkdir -p /opt/kontur785/shared
scp infra/deploy/.env.prod.example user@server:/opt/kontur785/shared/.env
# заполнить .env на сервере (COOKIE_SECRET, POSTGRES_PASSWORD, DOMAIN, ...)

./scripts/deploy.sh
```

`deploy.sh` — это то, что просили: **вносить изменения локально и переносить их
на рабочий развёрнутый сайт одной командой.** Схема — capistrano-style releases:

1. Локально прогоняются typecheck + тесты + сборка. Падает хоть один шаг —
   деплоя не будет, старая версия на сервере продолжает работать.
2. `rsync` копирует рабочую копию в `releases/<timestamp>` на сервере.
3. На сервере: `docker compose build`, `prisma migrate deploy`, `docker compose up -d`.
4. Проверка `/api/health`. Не прошла — симлинк `current` НЕ переключается,
   старый релиз как работал, так и работает (нулевой простой на неудачном деплое).
5. Успех — `current` переключается на новый релиз, старые релизы (кроме
   последних `DEPLOY_KEEP_RELEASES`) удаляются.

Откат без пересборки на любой сохранённый релиз: `./scripts/rollback.sh` (без
аргументов — список релизов), `./scripts/rollback.sh <id>` — откат.

Первый администратор платформы создаётся на сервере отдельной командой
(`reference/SERVER.md` §7, обязательная смена пароля при первом входе):

```bash
docker compose -f infra/docker-compose.prod.yml exec api \
  node dist/scripts/createAdmin.js --inn 7726345678 --login admin --password '<временный>' --fio "Фамилия И.О."
```

Начальные эталонные каталоги (SERVER.md §7 «эталонные справочники — как
начальные данные миграции»; обе команды идемпотентны — не перезапишут то, что
уже опубликовал методист через `/panel`):

```bash
docker compose -f infra/docker-compose.prod.yml exec api node dist/scripts/seedChecklists.js
docker compose -f infra/docker-compose.prod.yml exec api node dist/scripts/seedStageDocs.js
```

## Что дальше (по приоритету, `reference/SERVER.md` §6)

1. **Годовой цикл клиники** — методист публикует эталон (`cycle_master`, уже
   готово в `/panel`), но его разбор в помесячный план проверок клиники
   (`cycle_live` → авто-строки в `audit_plan`) не перенесён. `PlanService`
   пока покрывает только ручные записи плана — для реальной работы достаточно,
   для авто-планирования на год вперёд — нет.
2. **Филиалы** — прототип ведёт систему качества по каждому объекту клиники
   отдельно (`branch` уже есть как поле плана/этапов), но управление списком
   филиалов не перенесено — сейчас везде подразумевается один объект.
3. **Оборудование и «Сводный отчёт»** в мобильном обходе — читаются
   исполнителем уже сейчас (`equip_pos`/`equip_fill`), но запись через сам
   экран обхода не перенесена: обе фичи завязаны на годовой цикл (п.1).
4. **Самообследование** — прогон клиники по чек-листам надзора с выгрузкой
   пакета для инспектора. Не перенесено; частично закрывается тем, что
   документы уже открываются по факту оплаты и выдачи (`StageService`).
5. **Дашборд и каталог клиентов** в панели — обзор по всем клиникам одним
   экраном. Сейчас платформа действует по ИНН конкретной клиники (как уже
   работает выдача документов) — рабочий, но не самый удобный способ для
   десятков клиник одновременно.
6. **Остальные 5 операций «второй руки»** (публикация тарифов, удаление
   тарифа, массовая операция >20 клиник, выдача документа без оплаты) —
   движок (`SecondHandService` + `container.secondHandHandlers`) общий и
   готов, добавление новой операции — это новый пункт в реестре плюс вызов
   `secondHand.request(...)` из нужного места, без изменения инфраструктуры.
7. **Провайдер SMS/email** — заменить `ConsoleNotifier` (`apps/api/src/infra/memory/notifier.ts`)
   на реальный шлюз (см. `.env.example`: `SMS_PROVIDER_API_KEY`, `EMAIL_PROVIDER_API_KEY`).
8. **Объектное хранилище файлов** — `LocalDiskFileStorage` (`apps/api/src/infra/files/`)
   держит фото обхода на диске сервера; порт (`FileStorage`) готов, замена на
   S3-совместимое хранилище — один новый адаптер, без изменений в `WalkService`.
9. **Платёжный шлюз** — сейчас оплата этапа идёт только «по счёту» с ручным
   подтверждением оператором (`PaymentService`); эквайринг, автопродление —
   `reference/SERVER.md` §6.7.
10. **Хостинг в РФ + уведомление РКН** (152-ФЗ) — до продажи первой реальной
    клинике с персональными/медицинскими данными.
11. Чек-лист приёмки после переноса каждого экрана — `reference/SERVER.md` §9.

## Известные ограничения (говорим прямо, не прячем)

- `mustChange` (обязательная смена пароля после `createAdmin`/`adminSetPassword`)
  сейчас только возвращается в `/api/auth/session` — фронтенд должен сам
  показать экран смены пароля и не пускать дальше; сервер пока не блокирует
  остальные эндпоинты по этому флагу. Добавить перед первым реальным клиентом.
- Все четыре кабинета на фронтенде — клиентские компоненты (`'use client'`):
  до гидратации страница пустая (нет SSR данных сессии). Стоит рассмотреть
  серверные компоненты с чтением cookie на сервере.
- «Сотрудники и матрица ответственных» в `/clinic` — упрощённая версия
  прототипа: без филиалов, учёта обучения по ИСМП и статуса «уволен»; матрица
  назначает ответственного на ПРОИЗВОЛЬНОЕ имя документа (текстом), а не на
  привязанный каталог направлений 785н.
- «Каталог этапов» и «Годовой цикл» в `/panel` редактируются как JSON-текст, а
  не вложенной формой — осознанное упрощение: под структуру `Stage[]`/
  `CycleMaster` строить полноценный конструктор в этом заходе избыточно,
  текстовый редактор полностью рабочий и проверяется тем же API.
- Разбивка документов прототипа (блоки `b01`–`b09`, реальные названия из
  `reference/prototype/Личный кабинет ВКК.dc.html`) по этапам 1–4 в
  `seedStageDocs.ts` — самостоятельная реконструкция по смыслу офферов
  этапов, а не проверенная копия внутренней связки прототипа
  (`blocks_catalog`/`doc_catalogs`/`block_tpls`/`block_pins`), которая
  слишком плотно завязана на ещё не перенесённый годовой цикл. Тексты
  шаблонов документов (`{{org}}`/`{{inn}}`/`{{date}}`/`{{responsible}}`) —
  рабочая, но собственная реализация подстановки, не копия конкретных
  бланков (сами бланки прототип не хранит как текст).
- В прототипе обещано, что при завершении обхода «система создаст... план
  CAPA» — на деле в прототипе этого кода нет (проверено: находки не пишутся
  никуда, кроме текста экрана). Перенесено то, что реально работает: клиника
  видит находки и превращает их в мероприятие вручную (`POST /api/clinic/capa`,
  раздел «Находки» в `/clinic`) — не выдуманная автоматика, а рабочий цикл.
- Оплата этапа — только «по счёту» с ручным подтверждением оператором;
  реального эквайринга нет (см. «Что дальше», п.9).
- Офлайн-очередь обхода (`apps/web/src/app/walk/page.tsx`) хранится в
  `localStorage` одним общим ключом на вкладку — этого достаточно для
  «потерял сеть на минуту в кабинете», но не для многодневной работы без
  связи на нескольких устройствах одновременно. Идемпотентность на сервере
  (`opId`) готова к более надёжной очереди (IndexedDB + Background Sync),
  когда она понадобится.
- Панель не показывает список клиник — платформа действует по явно указанному
  ИНН (как и выдача документов), а не выбирает клинику из каталога (см. «Что
  дальше», п.5).
- Визуальная сверка с прототипом на 390/820/1440 px (`reference/CLAUDE.md`)
  не выполнялась в реальном браузере в рамках этой сессии — только
  `next build` и HTTP-смоук (страницы отдают 200, вёрстка не проверена глазами).
  Сделайте её перед показом клиенту.
- Единственный настоящий e2e прогон — HTTP-уровень (`apps/api/src/http/app.test.ts`),
  не браузерный. Playwright/Cypress ещё не подключены.
